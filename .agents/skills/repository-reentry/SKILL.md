# Program Specification repository re-entry

## Contract

- **What:** A repository-local method for recovering settled, current, open,
  and next program state.
- **When:** Work resumes after a handoff, branch or pull request changes, or
  source, signed release evidence, constellation coordinates, current
  coordination records, and public projection appear to disagree.
- **Boundaries:** Runnable source and tests define current Program behavior.
  Signed release evidence defines accepted baselines. Each sibling repository
  retains authority for its own released behavior and observations. Contract
  and evidence authority remain with their defining sources; delivery records
  and publishes their bytes.
- **Result:** One authoritative source path, one current coordination surface,
  the material difference among records, and one bounded next move.

## Rules

### Rule: Current source and accepted release answer different questions

Read the working branch for current Program behavior. Read signed tags,
promotion records, and constellation locks for accepted release subjects. Read
Pages manifests and hosted observations for what was published.

### Rule: The nearest carriers come before broad history

Read the root README, release role, status, constellation, constellation lock,
Coordination Horizon, and first receipt before searching the complete history.
Follow the exact Issue, pull request, or workflow only when current coordination
changes the move.

### Rule: Each suite member keeps its authority

Program owns shared intent and acceptance direction. Governance owns shared
schemas and language contracts. Enterprise owns active implementation and
configured observations. Simulation owns the selected future. Comparative owns
admission, comparison, and reports.

### Rule: Release and projection identities remain separate

Record tag object, release commit, tree, archive digest, source revision, Pages
manifest, and public origin independently. A public presentation can advance
while accepted contract meaning remains stable.

### Rule: Existing work remains intact

Identify unrelated worktree changes and neighboring worktree branches before
editing. Surface the overlap and keep each collaboration's work with its
current owner.

### Rule: Stale status language becomes visible

When a current coordination record describes a completed route as waiting,
name the difference and reconcile that carrier through its owning validator.
Historical Issues, comments, and immutable release evidence retain their
temporal record.

## Operating sequence

1. Run `git status --short --branch`; inspect local, remote, tag, and open
   pull-request state.
2. Read `README.md`, `release/repository-role.json`, `STATUS.yaml`,
   `constellation.json`, `constellation.lock.json`, `coordination-horizon.json`,
   and `first-receipt.json`.
3. Identify the requirement, shared contract, example, release carrier,
   receiving repository, Pages source, and tests that own the task.
4. Resolve the accepted Program subject and every material sibling coordinate.
5. Inspect the live Issue, pull request, and hosted check only where current
   status or authority changes the route.
6. State settled, current, open, and next terrain; identify any stale carrier.
7. Choose one source path, one receiver, and one completion event.

## Completion

Re-entry completes when a collaborator can name current Program behavior, the
accepted release subjects, the authoritative suite member for each material
claim, the public observation when one exists, the next bounded move, and the
records from which work can continue.
