# Tagged constellation site release

## Desired receiving state

Prepare one reviewable site-release candidate that binds accepted source,
allowlisted generated bytes, an immutable publication-commit tag, a named
publication receiver, and a recoverable prior carrier.

[Program #77](https://github.com/driftframestudios/lims-eln-program-specification/issues/77)
owns this route and its receiving packet. Preparation can finish with the
candidate private and every activation decision still held. This runbook is
working guidance; its private exercise and receiving acceptance remain explicit
checkpoints.

Reuse the [constellation contract release handoff](constellation-contract-release-handoff.v0.1.md)
for shared contract and package coordinates. Repository releases, package
versions, site releases, source carriers and images retain separate identities
and approval routes.

## Entry, authority and safe pause

Begin with the current #77 packet, the SQL owner's settlement or named hold,
and the source owners' review returns. During SQL refinement, keep the source
cut and successor tag value pending. Current branch heads are provisional
orientation, not frozen release inputs.

Each invocation names its action mode and stopping event. Read-only assessment
does not grant builds, scans, configured runs, source merges, tag creation,
publication pushes or rollback activation. Request the particular next action
when its prerequisites are ready.

This route keeps all five source repositories private. Public Pages delivery
does not change repository or image visibility. The allowlisted,
ancestry-isolated public-source carrier remains the separate
[Program #65](https://github.com/driftframestudios/lims-eln-program-specification/issues/65)
tranche; a site release neither publishes that carrier nor closes its gates.

## Ordered preparation and approval route

### 1. Select the accepted source cut

**Owner:** SQL and repository source owners; the authorized maintainer retains
main promotion.

Receive SQL settlement, independent review and affected security dispositions.
Obtain separate approval for any required main merges, then record the accepted
full source commits and relevant contract/package bindings in #77. Reuse valid
owner evidence and renew only the observations affected by changed inputs.

**Checkpoint:** Every selected source has an exact identity, acceptance state
and owner. A remaining source or review hold keeps the cut pending.

### 2. Prepare private candidates

**Owner:** Each site's existing builder and verifier, under a scoped execution
grant.

Use clean, named source and the publisher's declared dependency/build profile.
Keep proof inputs and fresh output outside source worktrees where the owning
builder requires it. Record complete allowed membership, generated inventory,
manifest digest, source revision and proposed publication commit.

Use the existing reproduction and route checks. Preserve attribution,
licenses, CNAME, schema identities and exact-version retrieval paths. Review
outbound links and public content; keep raw diagnostics, protected locators and
credentials with their authorized owner.

Run the fitting canary-proven public-boundary observation only when authorized,
naming its exact candidate scope and evidence limits. Source scans and earlier
image dispositions do not establish the state of a newly generated carrier.

Prepare publication history through the existing generated branch or an
explicitly reviewed isolated carrier, keeping private development history out
of the publication lineage. Candidate preparation leaves remote branches,
Pages settings and DNS unchanged.

**Checkpoint:** An independent reviewer can identify the complete candidate,
its source and allowed content, fitting checks, unresolved gates and prior
accepted carrier. A failed check leaves the current public site intact.

### 3. Exercise recovery privately

**Owner:** The artifact owner and release reviewer.

Record the prior accepted publication commit, site tag and manifest digest in
the same #77 packet. Under the granted preparation scope, recover its complete
artifact into a separately owned private destination and verify the prior
inventory. This exercise moves no publication branch and activates no rollback.

**Checkpoint:** The prior carrier is recoverable without replacing the
candidate or changing either tag.

### 4. Approve the immutable site identity

**Owner:** The human release authority.

The existing `pages-YYYY-MM-DD.N` precedent uses annotated tags targeting
publication commits. The annotation records the source commit and manifest
SHA-256. Preserve that relationship unless a separately reviewed policy change
selects another mapping. Choose the next value only for the accepted candidate.

Obtain explicit tag-creation approval. Bind the approved tag to the reviewed
publication commit and exact source/manifest relationship. Keep existing tags
immutable; changed content receives a successor identity. Tag creation and any
remote tag push retain their own grants.

**Checkpoint:** Source, generated bytes and publication commit have one
unambiguous release identity. A missing approval leaves the candidate untagged.

### 5. Approve publication and observe delivery

**Owner:** The human publication authority and each site's publication receiver.

Obtain separate approval for the exact candidate and target publication branch
before any push. The configured `pages` or `docs` update activates delivery.
A tag or successful build is not that publication grant. Preserve existing
domain configuration unless a separate change is authorized.

After authorized publication, record the deployment commit, hosted build
result, manifest binding and the fitting signed-out byte, route and visitor
observations. Append delivery evidence to the receiving packet without
rewriting immutable tags or manufacturing self-referential artifact digests.

**Checkpoint:** The return distinguishes prepared bytes, approved publication
and observed delivery. On a delivery failure, retain the failure evidence and
request the bounded recovery decision. Repointing or redeploying a prior
carrier is a separately authorized rollback, not a tag rewrite.

## Handback and re-entry

Keep one compact receiving packet in #77 and link the source owners' evidence:

```text
Selected sources and acceptance state:
SQL/review/security holds:
Candidate publication commits and manifest digests:
Allowed membership and normalized check results:
Prior carrier, tag and private recovery result:
Proposed or approved site tags and exact targets:
Main/tag/publication approvals, each separately named:
Delivery standing and observation limits:
Next owner, requested action and re-entry event:
```

Return here when SQL settles, an accepted source changes, a review or security
decision arrives, or the human grants the next action. A changed source or
carrier reopens its affected bindings and checks. An absent grant leaves
existing sites, tags and repository visibility unchanged.
