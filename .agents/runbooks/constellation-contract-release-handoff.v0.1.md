# Constellation contract release handoff

## Desired receiving state

An accepted Program contract reaches each constellation repository through one
exact Program source coordinate, byte-identified generated projections,
representative examples, migration notes, a receiver-specific Issue and pass
condition, and a retained human decision for publication or deployment.

Completion means every active receiver can identify:

- the Program contract identity and semantic version;
- accepted commit, tag when released, Git tree, and relevant content digests;
- canonical source paths and generated schema or example bytes;
- compatibility direction, migration note, and superseded identities;
- its own bounded adoption result and evidence mode;
- the Program condition for coordinated release settlement; and
- the exact human-held publication, API activation, deployment, real-data, or
  regulated-acceptance decision that remains outside the handoff.

[Program Issue #51](https://github.com/driftframestudios/lims-eln-program-specification/issues/51)
owns this runbook. The contract's active Issue owns acceptance; for the first
exercise that owner is [Issue #50](https://github.com/driftframestudios/lims-eln-program-specification/issues/50).

## Entry condition and safe non-entry behavior

Enter after the Program contract owner accepts canonical source, examples,
compatibility behavior, generated projections, and migration notes at a named
revision. A review branch or integration commit can support a review handoff;
only a completed protected promotion supplies a released Program coordinate.

When source acceptance, generated-byte parity, migration behavior, or receiver
Issues remain incomplete, preserve the latest accepted Program subject and
return the missing gate to its owner. Receiving repositories can inspect the
candidate while adoption and release claims remain pending.

## Ordered phases

### Phase 1 — Confirm the accepted contract subject

**Owner:** The active Program contract Issue and authorized Program maintainer.

**Action mode:** `observation_only` for acceptance inspection; source changes
remain with the contract Issue's implementation grant.

1. Identify contract name, semantic version, canonical source paths, accepted
   commit or review coordinate, and release state.
2. Confirm the active Issue's acceptance criteria and review disposition.
3. Distinguish candidate, integration, and protected release coordinates.

**Checkpoint:** One Program subject owns the proposed meaning and has a truthful
lifecycle state. A reviewed candidate establishes accepted review content; it
does not establish a later protected release coordinate.

**Recovery:** Return source or acceptance gaps to the contract Issue. Keep the
last accepted version available to receivers.

**Stop condition:** Stop handoff when the source subject, semantic version, or
acceptance state cannot be named exactly.

### Phase 2 — Close generated carriers, examples, and migration notes

**Owner:** Program canonical source owns meaning; repository generators own
their projections; the contract Issue owns migration intent.

**Action mode:** `observation_only` for parity checks; correction requires the
active source grant.

1. Inventory every generated schema, example, manifest, package resource, and
   documentation carrier that travels with the contract.
2. Verify each generated carrier through its repository command and record
   content digest or byte identity where governed.
3. Bind representative and boundary examples to the contract version.
4. Record additive, breaking, deprecation, replacement, and rollback behavior
   in migration notes.

**Checkpoint:** Generated carriers agree with canonical source, and a receiver
can distinguish validation input, serialization output, enforcement
projection, and explanatory example.

**Recovery:** Change canonical source or the owning generator, regenerate once,
and repeat parity checks. Preserve a prior accepted carrier until its
replacement passes.

**Stop condition:** Stop release handoff when generated bytes, example
coordinates, dependency closure, or migration behavior differ from accepted
source.

### Phase 3 — Form the Program coordinate packet

**Owner:** Program release owner prepares the packet; the protected promotion
route supplies final release coordinates.

**Action mode:** `observation_only` for packet formation. Tagging, promotion,
or publication requires its existing authority route.

Record:

- repository and contract identity;
- full commit, Git tree, signed tag object and peeled commit when present;
- reproducible archive or scoped content digest when governed;
- schema, example, migration-note, and package coordinates;
- validation commands, normalized results, environment, and evidence limits;
- superseded version and compatibility relation; and
- active Issue, pull request, and review or promotion state.

**Checkpoint:** The packet identifies one reproducible Program subject and the
bytes receivers must compare. Pending zero or review coordinates remain
explicit until protected promotion replaces them.

**Recovery:** Keep candidate coordinates typed as pending. Form another packet
only after a source, review, or promotion event changes the subject.

**Stop condition:** Stop any released-coordinate claim until the protected
route supplies and verifies the corresponding commit, tree, tag, and required
digests.

### Phase 4 — Bind one job and pass condition per receiver

**Owner:** Program names the shared handoff; each repository Issue owns its
adoption and evidence.

**Action mode:** `observation_only` for routing. Receiver implementation uses
the grant on its own Issue and branch.

| Receiver | Bounded job | Minimum pass condition |
| --- | --- | --- |
| Governance | Adopt shared schema, language, workflow, or review grammar that belongs there | Accepted Governance identity and validation result |
| Enterprise | Implement the accepted contract or adapter in a named configuration | Configured behavior and release-conformance evidence |
| Simulation | Exercise declared synthetic scenarios and assumptions | Version-bound selected-future result with production effect `none` |
| Comparative | Pin producer inputs, normalize, compare, and adjudicate | Exact pair coordinates and challengeable difference report |
| Program | Update bindings and acceptance only after receiver evidence is ready | Coherent candidate whose external roles retain their true status |

Each receiver gets the Program packet, its own Issue, the objects it must
consume, evidence mode, checks, known limits, and return event.

**Checkpoint:** Every active job has one repository owner and cannot inherit
another repository's evidence or authority by implication.

**Recovery:** Route a semantic or compatibility mismatch to Program or
Governance. Route an implementation, scenario, or comparison gap to its
respective owner while the Program source stays unchanged.

**Stop condition:** Stop the affected receiver when its Issue, accepted input
coordinate, or pass condition is absent. Other independent receivers can
continue.

### Phase 5 — Preserve human-held and protected decisions

**Owner:** The named human, accountable domain role, or protected platform
receiver retains the decision.

**Action mode:** `observation_only` unless a later task explicitly grants the
state-changing action.

Identify separately:

- public schema host and publication timing;
- dynamic API activation, provider, hostname, DNS, credentials, and budget;
- dependency adoption and upstream contribution;
- real payer policy, patient, customer, or operational material;
- Clinical, Scientific, Quality, Regulatory, Security, Operations, and
  population or community acceptance; and
- release promotion, deployment, and rollback activation.

**Checkpoint:** The handoff makes every retained decision visible beside the
artifact that would be affected. Repository readiness remains useful without
being described as external activation.

**Recovery:** Continue with static, local, simulated, or candidate evidence
that fits the current grant. Return one concrete choice and its consequences to
the retained owner.

**Stop condition:** Stop before changing protected external state or making an
accountable acceptance claim without its named grant.

### Phase 6 — Reconcile returns and close the release route

**Owner:** Program release owner synthesizes receiver returns;
`constellation-coherence-reconciliation` owns exact coordinated settlement.

**Action mode:** `observation_only` for synthesis; Program source or release
changes follow their existing review and promotion route.

1. Collect one decision-bearing return from each active receiver.
2. Verify exact Program input coordinates, receiver output coordinates,
   compatibility results, and evidence modes.
3. Apply constellation coherence reconciliation before updating a coordinated
   lock or public summary.
4. Return completion, friction, or blocker to the active Program Issue with the
   next receiver and exact re-entry event.

**Checkpoint:** Program can distinguish accepted shared meaning, receiver
adoption, simulated behavior, configured observation, comparison judgment,
coordinated release, and public delivery.

**Recovery:** Preserve accepted release subjects and route only the divergent
relation to its owner. A changed source coordinate reopens affected receiver
checks.

**Stop condition:** The runbook stops when the coordinated result is settled or
when one named owner holds a remaining gate with an observable release event.

## First-use posture for the Issue #50 family

The Issue #50 contract-evolution exercise establishes the handoff's candidate
shape but does not satisfy this runbook's entry condition yet. The first live
handoff begins after canonical identities, schemas, examples, dependency
closure, compatibility rules, and migration notes are accepted. That event
will determine whether this runbook advances from `working` to `exercised` and
will supply any decision-changing revision.

Until then:

- Synthetic Hospital v1.3 remains a pinned external reference and bounded
  adapter-probe candidate;
- generated insurance text remains source-exact input with generated
  provenance;
- receiver Issues can refine their local plans against Issue #50 vocabulary;
  and
- publication, API activation, domain configuration, deployment, and
  accountable acceptance remain with their named decision owners.
