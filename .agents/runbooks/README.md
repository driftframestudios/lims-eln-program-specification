# Program collaboration runbooks

Runbooks give human and AI collaborators a re-entrant route through a known,
multi-phase Program procedure. They work beside the repository's current
owners:

- GitHub Issues retain outcome, scope, acceptance, and current work state.
- Program contracts and examples define shared meaning.
- Each constellation repository retains its named implementation, simulation,
  comparison, or governance authority.
- A runbook orders an already known route. It supplies no publication,
  deployment, dependency-adoption, real-data, regulated-acceptance, or
  upstream-contribution authority.

Tracked runbooks are public-possible. They depend on public repository sources,
public links, and repository-local explanations. Exact protected workspace
coordinates remain with their authorized resolver.

## Header and standing

Each runbook uses the following metadata profile:

```yaml
---
title: Short descriptive title
version: 0.1.0
status: working
audience: human_and_ai_collaborators
source_band: public_possible
task_type: operational_collaboration
---
```

`working`, `exercised`, `stable`, and `retired` describe observed maturity.
They neither grant authority nor replace current Issue and pull-request state.

## Shared phase contract

Every phase names:

- its current owner;
- one action mode;
- the actions already settled for that route;
- a checkpoint and what the observation establishes;
- a useful recovery state; and
- the condition that stops the phase or suspends later mutation.

A handback uses one receiving surface and returns the changed or inspected
source, normalized evidence result, coverage boundary, current Issue, next
receiver, and exact re-entry event. Raw logs, credentials, protected routes,
query-bearing URLs, private workspace coordinates, and user-specific paths stay
with their existing authorized owner.
