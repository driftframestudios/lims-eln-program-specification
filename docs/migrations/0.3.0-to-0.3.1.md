# Migration guide: 0.3.0 to 0.3.1

Release `0.3.1` strengthens the control plane while preserving the domain
requirements and selected-future closure identifier from `0.3.0`.

## Consumer actions

1. Update specification bindings from `spec-v0.3.0` to `spec-v0.3.1`.
2. Resolve governance through the accepted `governance-v2.1.0` annotated tag,
   commit, Git tree, and reproducible Git archive recorded in
   `constellation.lock.json`. Keep the Git tree and archive SHA-256 as separate
   identities. Schema release 2.1.0 retains the stable `/v2.0/` identifier
   family.
3. Resolve implementation through semantic release `implementation-v0.3.2`
   and Git tag `v0.3.2`. Verify its signed tag object, commit, tree, archive,
   release-role contract bindings, selected-future closure, and bound artifact
   bytes through `scripts/validate_pinned_sources.py`.
4. Treat `receipts/promotion-receipt.json` as the release-state evidence
   record. Candidate state carries zero provenance and a null release
   coordinate. Released state carries observed provenance, check contexts,
   merge admission, independent-review completion, and the GitHub review record.
   `receipts/promotion-observation-spec-v0.3.1.json` carries the distinct
   post-tag observation. Its verifier reproduces the signed release subject
   and derives the later observation-carrier commit directly from Git.
5. Preserve the standing `main` controls as their own record: deletion and
   non-fast-forward protection, one approval, CODEOWNER review, last-push
   approval, and review-thread resolution. For this release, record the
   configured ordinary bypass, completed deputized independent review, and
   GitHub's empty formal-review collection as distinct facts. Keep `develop` as
   the lean integration branch. Record the lightweight pull-request proof as an
   observed context while the required-check list remains empty until a
   separate review establishes its stable context name, evidence value, and
   recovery route.
6. Run `scripts/validate_pinned_sources.py` with all sibling repository roots
   during settlement. The command accepts a candidate only when
   `--allow-pending` is explicit.
7. Run the language, program, secret-shape, and unit-test checks before
   promotion.
8. Bind consumers to `DATA-CONTRACT-001` and
   `DATABASE-MIGRATION-CONTRACT-001`. Implementations satisfy its tool-neutral
   capability requirements through the selected Flyway Community 13.0.0
   profile and publish an immutable migration head, executable artifact digest,
   validate/info evidence, retained-test results, and catalog digest before
   settling the database release manifest.
9. Treat the eight records in `receipts/database-open-receipts.json` as
   future-observed obligations. Close them with configured-environment,
   representative-rehearsal, recovery, security, and accountable acceptance
   evidence at the implementation release coordinate.
10. Install `lims-eln-program-specification` 0.3.1 from the reviewed Program
   merge commit through the authenticated PEP 508 form documented in the
   README. A sibling editable install remains available for local development.
   During consumer release conformance, read PEP 610 `direct_url.json`, match
   `vcs_info.commit_id` to the reviewed binding, reproduce the scoped
   package-source digest, verify package and contract versions, then load the
   operation catalog, Golden Specimen scenario, both shaped observations, and
   every released schema. The canonical HTTPS requirement receives credentials
   from the consumer's Git credential helper or short-lived GitHub App token;
   credential values stay with that authentication owner.
11. Emit the shared Golden Specimen comparison fields through
   `GoldenSpecimenResultProjection` at `result.projection`. Keep producer-owned
   detail at `result.producer_detail`, and preserve evidence mode, provenance,
   assurance stage, approvals, and classification in the surrounding
   observation. Comparators accept the projection identity and version through
   its declared `exact-version` rule.

## Compatibility

The bounded-caller operation identifiers, proof classes, open observed
receipts, and selected-future closure identifier remain stable. Its accepted
signed-release content and digest advance together.
Release metadata, validation strictness, and automation contexts advance in
this patch. The Program binds the signed Implementation 0.3.2 release subject,
its semantic release-role contract, and its material release artifacts without
coupling the Implementation version to the Program version. The Program also
carries the exact 2.0.1 bundle bytes accepted by
the signed Simulation and Comparison releases. Governance 2.1.0 validates the
current Program projection while the Comparison release truthfully retains its
historical 2.0.1 binding. The Program lock records that binding as an exact
untagged Governance commit, tree, and archive. Cross-repository validation
confirms its place in the Governance 2.1.0 lineage and runs the historical
validator against the signed Comparison Machine Node and first receipt.
When the Program tag is selected for the deliberate full proof, the workflow
matches its name to the lock, confirms its peeled commit is the dispatched
source, and verifies its repository-trusted signature.

The Golden Specimen result projection is additive to the existing observation
envelope. Existing generic result objects remain valid. Producers can adopt the
typed projection independently, and a comparator can continue using the
generic envelope until it explicitly selects the new projection coordinate.

The additive database contracts use version `1.0.0` and carry their own stable
identities. They enrich release `0.3.1` while preserving the existing bounded
caller identifiers, canonical closure, and nine original open receipts.

The selected Flyway profile replaces migration ordering, history, checksum,
coordination, and status behavior previously projected onto custom orchestration.
Existing end-to-end domain tests and parameterized clean, predecessor, failure,
replay, and convergence scenarios remain the transition oracle. Vendor upgrades,
cross-vendor data movement, semantic reconciliation, restore, and accountable
acceptance retain their distinct program boundaries.
