# Contract package 0.3.1 to 0.4.0

Package `0.4.0` adds the external benchmark and administrative-context family
while the Program release remains `spec-v0.3.1`. Consumers can continue using
`0.3.1` until they need this family. Adoption is an explicit receiving change.

## Added public surface

- Nine strict contract objects and one aggregate relationship boundary.
- A source-neutral administrative-adapter schema and a dependency-closed
  aggregate schema.
- One canonical dependency-closed bundle and three deterministic,
  byte-checked reader projections.
- Typed loaders for the canonical bundle, adapter contract, and two focused
  examples.

Existing bounded-call, evidence, observation, specimen, scenario, Golden
Specimen, and operation-catalog interfaces keep their current behavior.

## Receiving sequence

1. Wait for the reviewed merge to supply the package `source_commit` and scoped
   digest in `release/contract-package-coordinate.json`.
2. Install that exact full commit through the repository's authenticated PEP
   508 route or an adjacent editable checkout.
3. Confirm distribution and import version `0.4.0`, then load every name in
   `SCHEMA_RESOURCE_NAMES`.
4. Load the canonical bundle and all three reader-specific examples; run the
   administrative-example projection check when receiving package bytes.
5. Select the object and example that answer the receiving Issue; retain raw
   input values and release-scoped subject identities.
6. Add implementation, simulation, comparison, or governance behavior only in
   the repository that owns it.

## Compatibility notes

The package version advances because package content and its scoped digest
change. The family itself begins at `1.0.0`. Existing consumers receive no
silent runtime behavior change unless they import or load the new surface.
Generated schemas are exact byte projections of the Python models. A receiver
that persists or exchanges these records should pin the contract identity,
version, package source commit, and schema bytes it accepts.
The canonical bundle owns every shared example record; committed standalone
examples are generated projections rather than parallel authorities.

Policy evaluations explicitly name
`urn:driftframe:lims-eln:policy-input-digest:1.0.0`; counterfactual arms also
name `urn:driftframe:lims-eln:administrative-decision-digest:1.0.0`. The first
binds cited, normalized policy inputs and the second binds the complete
referenced decision. Receivers should calculate these profiles from canonical
material rather than treating their digest fields as caller declarations. The
policy evaluation carries that material directly; the aggregate schema and the
package exports expose its machine-readable shape and supported builder.

## Recovery

A consumer can return to its reviewed `0.3.1` commit because the new family is
additive and existing interfaces retain their shapes. Records created under
the new family remain data with a `1.0.0` identity; preserve them while the
consumer restores its prior code. A source, policy, vocabulary, population,
review, or digest change follows the invalidation route in
[`EXTERNAL_ADMINISTRATIVE_CONTRACTS.md`](../EXTERNAL_ADMINISTRATIVE_CONTRACTS.md).

The migration establishes a contract-adoption path. Population, payer,
clinical, deployment, and regulated-acceptance evidence continue through their
separate receivers.
